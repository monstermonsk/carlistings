Crankshaft connector catalog and dealer portal specification

Engineering research and implementation contract · 11 October 2026. Crankshaft owns the dealer-facing portal. Dealers do not need a bespoke integration workshop. They choose their software from a supported list, authorize a connection when that vendor permits it, and use the same Crankshaft screens regardless of vendor. The adapter layer translates that standard interface to vendor APIs, approved feeds, or CSV. This catalog is a researched starting set, not a claim that every vendor grants Crankshaft access today. Vendor permissions and documentation can change; recheck a row before enabling a production connector.

1. Product boundary and user journeys

  1. A dealer administrator creates a dealership and locations in the existing Crankshaft identity system. Crankshaft stores its own dealer staff directory: salesperson ID, name, location, role, active status, allowed call types, working hours/timezone, routing priority, forwarding destination, CRM user ID(s), and effective dates. The directory is authoritative for Crankshaft routing and reporting; an authorized CRM staff sync can propose updates but does not silently remove a live transfer target.
  2. The administrator chooses inventory/DMS, CRM, syndicator/website, and marketplace destinations in Connections. They complete OAuth where supported or enter a vendor-issued API key/token in a secure one-time form. Partner-gated products display Awaiting vendor access and the exact required authorization step. A dealer login/password is never used as a substitute for an API credential. CSV is an always-available output path.
  3. A salesperson selects a current stock unit and uploads real photos/phone video. Listing Tuner produces a reviewable listing. A dealer approver approves a specific immutable version. Crankshaft sends it through an authorized primary inventory/website/syndication route; direct marketplace sends run only where separately authorized. Export is available in CSV plus media manifest/ZIP.
  4. The already-built verifier and SignalWire router emit call/transfer events to Crankshaft after routing decisions. The portal displays each received call, requested vehicle if known, qualification, the agent(s) attempted, the agent who answered, duration, disposition, and linked lead/appointment. An administrator can correct assignment/outcome with an audit record. Listing/portal outages cannot block a live call.
  5. If the CRM grants write access, Crankshaft posts the qualified lead/call disposition and keeps the vendor receipt. If it grants read access, Crankshaft reconciles appointments and sales. If neither is available, export a standard call/lead CSV and import a dealer-provided outcome CSV. The portal remains usable without a CRM connection.

2. Canonical model and synchronization

Core keys: tenant_id, location_id, staff_id (Crankshaft UUID), stock_lifecycle_id, listing_version_id, call_id (existing verifier ID), transfer_attempt_id, lead_journey_id, connection_id, external_record_id. Keep separate mappings (tenant, system, external_staff_id) ↔ staff_id and (tenant, system, external_stock_id) ↔ stock_lifecycle_id; names and VIN alone are not join keys. A stock ID can be reused after sale, so its lifecycle is versioned.

Tables: dealer, dealer_location, dealer_staff, staff_external_id, staff_schedule, routing_policy_version, provider_connection, provider_capability, provider_secret_ref, external_id_map, sync_cursor, sync_run, connector_receipt, stock_snapshot, listing_version, publication, call_event, transfer_attempt, call_assignment, lead_journey, lead_external_id, outcome_event, csv_export, audit_event. Scope all queries and object paths by tenant. Use append-only raw provider events and an idempotent normalized projection; record source timestamp, received timestamp, provider revision, mapping version, and correlation ID.

Call ledger minimum: call_id, location, incoming DID/source campaign, start/end/duration, caller display token (mask number by role), consent/recording flag, requested stock candidates/confidence, verifier result/reason/policy version, transfer attempts with target staff_id, initiation/ring/answer/end timestamps and provider status, answered_staff_id (nullable), final disposition, CRM lead ID/receipt, appointment ID, and listing attribution confidence. Distinguish attempted, answered, missed, voicemail, after_hours, service, and unassigned; never infer “routed to salesperson” merely from a dial attempt. Use SignalWire call/leg IDs to reconcile the existing router's events. Staff deletion is soft/effective-dated so historical call assignments remain readable.

Portal views and roles: dealer admin sees Connections, Staff & Routing, Listings, Calls, Outcomes, Exports, and Audit. Sales manager sees staff, calls, listing review, and outcomes for assigned locations. Salesperson sees own assigned calls and capture tasks. Crankshaft operator sees tenant-scoped support data but not provider secret values. Field-level masking applies to caller data and recording/transcript links. Pagination, date/location/staff/qualification filters, CSV download and audit trail are part of the Calls screen. Show late/missing provider events and reconciliation state, never a fabricated final result.

Sync directions and conflict policy: inventory/price/status are inbound from the dealer's selected system; approved copy/media are outbound to its permitted merchandising destination; call events are inbound from Crankshaft's existing verifier/router; qualified leads/dispositions are outbound to CRM if supported; appointments/sales are inbound from CRM/DMS if supported. Dealers set field authority in a standard preset per vendor, with an explicit override for exceptions. Price, sold state and dealer-required disclosures always pass a fresh source-revision gate before publish. Never let a downstream marketplace's transformed record overwrite the source stock. Polling/webhook cursors are per connection; webhook replay and duplicate messages are safe.

3. Standard connector contract

Implement one versioned internal interface; a provider implements only the capabilities it actually supports:

interface DealerConnector {
  manifest(): CapabilityManifest;                  // vendor, products, auth, scopes, directions, limits
  testConnection(connectionId): ConnectionResult; // no secret returned
  pullInventory(cursor?): AsyncIterable<StockDelta>;
  pullStaff?(cursor?): AsyncIterable<StaffDelta>;
  pushListing?(version, idempotencyKey): PublicationReceipt;
  removeListing?(externalId, idempotencyKey): PublicationReceipt;
  readPublication?(externalId): PublishedSnapshot;
  pushLead?(callId, lead, idempotencyKey): LeadReceipt;
  pullOutcomes?(cursor?): AsyncIterable<OutcomeDelta>;
  health(): ConnectorHealth;
}

CapabilityManifest is explicit per vendor + product + version + dealer entitlement, not a generic “API supported” boolean. Fields: inventory.read, listing.write, listing.remove, publication.read, staff.read, lead.write, outcome.read, webhook, csv.in, csv.out, auth kind, required scopes, media method, supported fields, field limits, cadence, rate limit, prerequisite agreement, and test/live status. The portal turns unsupported actions into a labeled export/manual path. Acceptance of a feed is accepted, not live; only a vendor readback or verified public VDP can set live. If the vendor never offers readback, display accepted / live unverified.

Build adapters with provider contract tests and recorded synthetic fixtures. For each write: validate normalized payload against the destination profile; upsert by stable external key; persist request hash and receipt; retry transient errors with backoff; reconcile external IDs; compare resulting URL/record when possible; alert on mismatch. Sold status cancels queued upserts and starts withdrawal through every connected path. A partner feed that republishes to several sites must report one hub receipt plus separate downstream verification, avoiding duplicate direct postings.

4. Connection and secret design

The UI flow is Select provider → Show supported directions and prerequisite → Connect/enter key → Validate scopes and location → Review field mapping preset → Test with synthetic or read-only record → Activate. For OAuth, use authorization-code flow with PKCE and state/nonce; redirect through a Crankshaft callback and store refresh/access tokens server-side. For API keys, a single-use HTTPS form posts directly to the secrets service; never echo the value or save it in the browser after submission. For vendor partner programs, hold Crankshaft application credentials separately from each dealer grant/subscription. A dealer cannot grant partner certification simply by pasting its own token.

Store secrets in a managed vault/KMS with envelope encryption and a reference in provider_connection, never plaintext in application tables, analytics, client JavaScript, CSV, logs or support screenshots. Record only provider, scopes, created/last-tested/expiry, fingerprint/last four where safe, and secret version. Restrict retrieval to that connector worker and tenant, rotate/revoke with audit, redact HTTP tracing, and disable outbound jobs on failed validation or revoked scope. SFTP adapters pin host keys, use per-dealer SSH keys and isolated folders; webhook receivers check signature, timestamp, replay window and tenant binding. Use TLS, least-privilege scopes, per-tenant rate limits, encrypted backups, and an operator break-glass log.

CSV fallback: export RFC 4180 UTF-8 inventory-listings-v1.csv (one row per stock/version/destination) with stock_id,vin,year,make,model,trim,price,mileage,availability,title,description,features,required_disclosures,hero_image_url,image_urls,video_urls,call_tracking_number,approved_at,version_hash; serialize array fields as JSON arrays inside correctly quoted CSV cells. Separate media-manifest.json carries filenames, ordering, SHA-256, mime type, dimensions and expiring signed URLs; optional ZIP serves importers that require local files. Export calls-v1.csv and outcomes-template-v1.csv separately; do not put caller PII into public listing exports. Include schema version, timezone/UTC, a sample file, field guide and row-level validation report. The listing CSV example and call CSV example are synthetic, with no real VIN or caller. A human downloads or a dealer-approved SFTP endpoint receives the file. Mark state exported, then record importer acknowledgment or dealer confirmation; do not call it published from file creation alone.

7. Build sequence and acceptance

Slice A: staff directory + call ledger + existing verifier/SignalWire event bridge. Replay calls with two transfer attempts, one answer, no-answer fallback and a corrected staff assignment; show the same result in portal and calls-v1.csv. Ensure portal/DB failure does not delay live transfer.

Slice B: connection UI + vault + manifest registry + CSV inventory/listing/call exports. Exercise key rotation, revoked scope, wrong tenant, bad SFTP host key, malformed row and receipt reconciliation. Publish the canonical schemas and vendor fixture harness before parallel adapters.

Slice C: first authorized inventory source and primary website/syndicator publisher, then one CRM lead/outcome connector. Require ten real pilot stocks, sold withdrawal, price revision, approval invalidation, receipt/live check, qualified-call-to-agent display and CRM outcome reconciliation.

Slice D: partner/API connector families (Fortellis, Tekion, OpenTrack, PBS, DealerBuilt) and feed families (HomeNet, DealerCenter, AutoManager, Frazer), prioritized by signed dealer demand and actual partner credentials. Marketplace adapters follow their own permission gates. All adapters run the same contract suite and are switchable per tenant.

No consultancy dependency: a dealer supplies the provider, product, location IDs, authorization and any allowed feed path through fixed screens. Crankshaft maintains provider presets and supports exception tickets when a vendor's contract varies. A partner agreement is a product enablement requirement, not a dealer-specific software inspection project. The portal remains functional in CSV mode throughout.
